# viewkit

The code that mdview, pyview, pdfview, pageview, plateview and texview share. It is not an app. It has no command of its own.

## Install

Install all the viewers and their Claude Code skills with two commands. The public repository `viewers` has all the viewers and `viewkit` in one repository:

```
git clone https://github.com/kostastsa/viewers-public ~/tools/viewers
~/tools/viewers/install.sh
```


`install.sh` does these steps. You can run it again, and it changes only what is not correct:

1. The skills use the paths `~/tools/viewers/APP`. If the clone of the repository `viewers` is in a different folder, the script links `~/tools/viewers` to it. A folder `~/tools/viewers` that is not a link stays, and the script uses it. With separate repositories, `viewkit` must be in `~/tools/viewers/viewkit`, and the script clones `mdview`, `pyview`, `pdfview`, `pageview` and `plateview` next to it.
2. It links each command into `~/.local/bin`.
3. It links the skills of `skills/` into `~/.claude/skills/` (or `$CLAUDE_CONFIG_DIR/skills/`).
4. It builds the macOS apps that open files from Finder.
5. It builds the shared Python interpreter of pyview (`pyview --setup`).
6. It tells you which external tools it cannot find: pandoc (mdview, pageview), poppler (pdfview), `claude` (the chat and the Oracle button) and `gh` (optional, for notes).

Options: `--update` (also pull the new commits), `--no-apps`, `--no-venv`, `--config-dir DIR` (a different Claude Code configuration folder, more than one is possible), and `--maintainer` (no effect now: all users get the `improve` skill). Run `install.sh --help` for the details.

With separate repositories, the folders must be in `~/tools/viewers`, because the skills use these paths. The clone of `viewers` can be in a different place. Each app adds `../viewkit` to its import path and stops with a clear message if the folder is missing. Python 3.9 or newer. Standard library only.

## Files

| File | Purpose |
|---|---|
| `serverkit.py` | The background server of an app: access key, grants file, start, stop, ping, and the restart when the app or the kit changes. It also serves the page files of `web/` at `/kit/NAME`, and the files of `web/vendor/` at `/kit/vendor/PATH` (`kit_asset`). It has no rules about who may read what. `app_host(name)` and `local_hosts(name)` give the host name of an app (`NAME.localhost`) and the accepted host names. `doc_label(p, others)` gives the short label of a document for the tab and the header. `Net(name, prefix)` gives the network address of a server: 127.0.0.1, or the Tailscale address with `PREFIX_BIND=tailscale` (and the names in `PREFIX_NAMES`), the host in the links, and the accepted host names. pyview and plateview use it. |
| `artkit.py` | The watermark art: figures down the left and right margins of a page (mdview and pageview). The figures are not in Git. They are in the art folder: `VIEWKIT_ART`, else `viewkit/art`, else `mdview/art`. `file(rel)` serves `/art/REL` (an empty manifest without the folder, so the page draws nothing). `scores()` serves `/api/art/scores`, and `vote_api(op)` serves `POST /api/art/vote`. A click on a figure adds 1 to its score, and a double click adds -1. All the viewers share the scores (`figures/scores.json`). |
| `datakit.py` | Data files for the viewers that show data (pageview, plateview): `read_table` reads CSV, TSV, JSON and JSON Lines as columns and rows, and `pdf_figure` makes a PNG of the first page of a PDF figure. |
| `claudekit.py` | The chat run: the environment, the command line, the process, and the stream-json lines of `claude -p`. The app keeps its own system prompt, tool lists, saved conversation, and the way it tells the page about news. `Oracle` is the background run that answers the comments of a document with a skill: a lock per document, one session per document, and a report at the end. mdview, pdfview, pageview, texview and plateview use it. pyview still has its own simple version. Accounts: each Claude Code configuration folder (`~/.claude`, `~/.claude-NAME`) is an account. `account_api` is the route `/api/account` of the apps, and the chat panel shows a selector before **New** when there is more than one account. Each document has its own account, in `~/.config/viewkit/accounts.json` (`VIEWKIT_ACCOUNT_FILE`). The last choice is also the account of the documents without a choice. `clean_env(doc=PATH)` sets `CLAUDE_CONFIG_DIR` from it, so the chat and the Oracle of the document use it from their next run. Without any choice, the runs use the `CLAUDE_CONFIG_DIR` of the server, or `~/.claude`. Before a `--resume`, `carry_session` copies the newest transcript of the session into the selected account, so a conversation continues after a change of account. |
| `improvekit.py` | The notes of the self-improving apps (`docs/self-improving-apps.md`). `add(app, app_dir, text, source, context)` makes a GitHub issue with the label `note` with `gh`, and adds the commit of the app. Without the network, the note waits in `~/.cache/viewkit/notes-queue.jsonl` and goes with the next note. The tracker (`tracker`): a note is a GitHub issue only when the `gh` user may push to the repository (the owner, or a fork). Else it is an issue of the local tracker (`localgh.py`), so a clone of the public repository never makes a public issue. `VIEWKIT_NOTES=github` or `local` sets the tracker. The layout (`mono_root`, `worktree_of`): each app is a repository of its own, or all the apps and viewkit are folders of the repository `viewers`. In `viewers`, a proposal has one worktree of the whole repository and one branch. `clean_context` makes the context from a page safe. `dash_api` is the route of the dashboard: the waiting notes (`~/.cache/viewkit/improve/APP-drafts.json`), Send all, and the list of the runs. `note_main` is the `APP note` subcommand. `try_main` is the `APP try N [FILE]` subcommand: the sandbox of a proposal, with the server of its worktree (`~/tools/viewers/wt/note-APP-N/APP`) on port 8900+N and copies of the files (`VIEWKIT_WT` changes the folder for the tests). pdfview uses it. `companions_of` gives the files that the sandbox copies with a document: the `companions` of `improve.json`, and the output of the `deps` subcommand of the live app when `improve.json` has `"deps"` (pageview: the data files and images of a page). It keeps only files of 50 MB or less in the folder of the document. |
| `improverun.py` | The background runs of the automatic loop: implement a note (a worktree, `claude -p "/improve implement"`, the tests, the push, the preview tab), change it from the feedback of the preview, accept it (merge, push, close the issue) or reject it. `improvekit.spawn` starts it. Its status and log are in `~/.cache/viewkit/improve/`. Before Claude changes a proposal again, the run rebases the proposal on `main` (`catch_up`), so the proposal and its sandbox have the newest code, for example a change of the kit. On a conflict, the proposal keeps its old base. The Claude runs of the loop use the account of the document of the note, and each copy of a document in the sandbox starts with the account of the document (`claudekit.set_account`). An app joins with `improve.json` (the tests, the port variable, the companion files, the optional `deps` subcommand, and the samples: representative documents in the repository that every preview opens, next to the document of the note). |
| `improve.json` | The test commands of all the viewers. The automatic loop runs them when a proposal changes the kit, in worktrees of the viewers next to the worktree of the kit. |
| `PRINCIPLES.md` | The design rules of the user for all the viewers. The `improve` skill reads it before each triage and adds rules from the decisions of the user. |
| `web/kit.js` | One global, `kit`. `kit.chatPanel(opts)` is the chat panel: the messages, Send and Stop, New, Ask only, the context chip, polling or the event stream, the resize grips (the size goes into `--kit-chat-w` and `--kit-chat-h` on `<html>`, and the app uses them in its CSS), the text size of the chat, and a **Copy** button on each code block of an answer. For the text size, put the focus in the panel (or click in it) and push ⌘/Ctrl+= (larger), ⌘/Ctrl+− (smaller) or ⌘/Ctrl+0 (the default). A pinch or Ctrl+wheel on the panel also changes the size, and does not zoom the document. The size goes into `--kit-chat-zoom` on `<html>`, and `kit.css` uses it as the CSS `zoom` of `chatMsgs`, `chatCtx` and `chatText`. The panel keeps its size. The browser keeps the text size in `localStorage` (`KEY.chatZoom`). Minimize keeps the scroll position of the messages, and Open puts it back. If the messages were at the end, Open shows the end again. The app gives the requests, the context, the answer renderer, and what to do when Claude changes the file (see the comment above `chatPanel`). `kit.chatAttention(...)` makes the Chat button pulse when an answer ends, puts a dot in the tab title, and sets the hotkey ⌘/Ctrl+S. `chatPanel` uses it. `kit.title(base)` keeps the dot when the app sets the title. `kit.tab({app, open, oracle})` draws the tab icon of the app (a blue M↓, a yellow-green Py, a red page, a teal square with bars). A badge shows the open comments, and a dot shows that Claude works or that an answer waits. The chat panel sets its own parts. `kit.docTitle(app, label)` sets the title (the name and the context), and `kit.crumbs(el, label)` shows the path in the header. `kit.copyText(text)` copies text to the clipboard. `kit.improveDash({app, get, post, context, onDone})` is the dashboard of the self-improving apps: ⌘/Ctrl+Shift+. opens it. New notes wait in a list (with the context of the app and the last buttons that the user clicked) until **Send all**, and a status list follows the runs (`improvekit.dash_api`). `kit.watermark({cols, isBg, post, toast})` draws the figures of the art folder (`artkit.py`) in the margins that `cols()` gives, and sends the votes with `post`. A figure with a higher score comes up more often. `kit.previewBand({get, post})` is the card of a preview tab, with Accept, Change… and Reject. The dashboard and the preview card are floating windows: drag the header to move the window, for example away from the part of the page that you try in the sandbox. A double-click on the header gives the default place back. The browser keeps the place in `localStorage` (`APP.dashPos` for the dashboard, `kit.previewPos` for the card), and the header always stays in the window. `kit.md(text)` makes a little safe Markdown (plain text only) for answers and comments, and `kit.typeset(roots)` typesets its maths with the MathJax copy of the kit. pdfview uses both. `kit.mathPrune()` removes from the list of MathJax the maths that are no longer on the page, so the old DOM does not stay in memory. `kit.typeset` calls it. An app with its own MathJax queue (mdview, pyview) calls it just before `MathJax.typesetPromise`. |
| `web/components.js`, `web/components.css` | The components of the viewers that show data: tables, grids (pivot), charts, figures, tabs, toggles, columns, callouts, stat cards, code with Copy, and widgets. `PV.enhance` makes them from the blocks of a pageview page, and `PV.make` makes one from an options object (plateview). The app defines the colour and font tokens. mdview uses `PV.enhance` with `keepTables: true` (the Markdown tables stay the tables of pandoc, so the comments of mdview stay on the cells) and `widgets: false` (a widget stays code). A stat card moves the nodes of its item into the card and does not copy the text. |
| `web/pdfpages.js`, `web/pdfpages.css` | `kit.pdfPages(opts)`: the pages of a PDF with PDF.js. It draws the pages near the view with a text layer, and it does the zoom (buttons, keys, pinch), the dark pages (images keep their colors), the links inside the PDF, the contents, the history of the jumps, and the place under the pointer in PDF points. A jump is a click on a link or on a section of the contents, or a page number. `pv.navKey(ev)` in the keydown handler of the app gives ⌘/Ctrl+[ (back) and ⌘/Ctrl+] (forward), as in a browser. The app paints its own marks on `pg.marks` in `opts.onPage`. When the same PDF loads again (texview compiles again), each page keeps its old drawing until the new one is ready. At most 12 pages have a drawing. An old drawing of a page far from the view goes after the next drawing. A page without images has one canvas only. The class `kitContents` on the panel of the contents gives the style of the list. texview uses it. |
| `web/kit.css` | The pulse styles, the resize grips, the text size and the **Copy** buttons of the chat panel, the dashboard, the preview card, and the watermark (`--kit-wm-opacity`). An app can change `--kit-shadow-btn` and `--kit-shadow-box`. |
| `app/build.sh` | Builds `~/Applications/NAME.app` for a viewer: a small macOS app that opens the files that you double-click in Finder with the command NAME. With `--default`, it also makes the app the default app of its file types, with `duti`. Each viewer calls it from its own `app/build.sh` with its file types. |
| `web/icons/` | The icons as PNG files. `APP-1024.png` is the flat drawing of `kit.js`, and the app builder makes the Finder icon from it (`tests/make_icons.py` makes it again). `APP-app.png` (256 px) and `APP.png` (64 px) are the app icons as macOS shows them, with its rounded shape and glass effect. The exception is pdfview: its `pdf-app.png` and `pdf.png` are the flat red page (`FLAT` in `tests/app_icons.py`). The tab icon and the folder pages use them, so the tab and the app have the same icon. After a change of an icon, run `tests/make_icons.py`, then `app/build.sh` of the viewer, then `python3 tests/app_icons.py`. |
| `web/vendor/fonts/` | IBM Plex Sans, Sans Condensed and Mono (WOFF2, SIL Open Font License, `LICENSE.txt`). plateview puts them in each plate. |
| `web/vendor/pdfjs/` | A local copy of PDF.js 4.10.38 (`pdfjs-dist` from npm): `pdf.min.mjs`, `pdf.worker.min.mjs`, `cmaps/`, `standard_fonts/`. pdfview and texview load it from the kit (`/kit/vendor/pdfjs/`). |
| `web/vendor/mathjax/` | A local copy of MathJax 3.2.2, the same as in mdview. pdfview loads it from the kit. mdview and pyview still use their own copies. |
| `tests/improve_test.py` | The test of the automatic loop for one app (`pdfview`, `mdview`, `pyview` or `pageview`): the dashboard, a question and its answer, a failed test and Try again, a change in the kit, the preview with the samples, Change, Accept of two repositories, and Reject. It uses copies of the app and of viewkit, a stand-in `gh` and a stand-in `claude`. It never changes the real repositories. |
| `tests/fake_gh.py` | A stand-in for `gh` in the tests of the notes. It writes each call to `FAKE_GH_LOG`. With `FAKE_GH_FAIL=1` it fails like `gh` without a network. With `FAKE_GH_NOPUSH=1` the user may not push to the repository. Set `VIEWKIT_GH` to its path, and `VIEWKIT_NOTES_QUEUE` to a test file. |
| `tests/notes_test.py` | The test of the tracker of the notes (GitHub, the local tracker, the queue without network) and of the commands of `localgh.py`. No network and no server. |
| `install.sh` | The installer of all the viewers and their skills (see Install). |
| `localgh.py` | The local tracker of the notes: the `gh` commands that the loop and the `improve` skill use (`issue create`, `view`, `comment`, `edit`, `close`, `list`), with the issues as JSON files in `~/.local/share/viewkit/issues/` (`VIEWKIT_ISSUES_DIR`). `localgh.py mode DIR` tells the tracker of a checkout. |
| `bin/gh` | Calls `localgh.py`. With the local tracker, the run of the loop puts `bin/` first in the `PATH` of Claude, so the skill can use `gh issue view`. |
| `skills/` | The Claude Code skills of the viewers. `install.sh` links them into the skills folder of Claude Code. `answer-comments` (mdview), `answer-cells` (pyview), `answer-pdf` (pdfview), `answer-page` (pageview), `answer-tex` (texview) and `answer-plate` (plateview) answer the comments of a document. These are the skills of the Oracle button. `page` and `plate` tell Claude how to write a pageview page and a plate. `improve` is the loop of the self-improving apps: notes in the dashboard of an app (⌘/Ctrl+Shift+.), proposals in a worktree, a preview with Accept, Change and Reject. It works with GitHub issues or with the local tracker. |
| `tests/fake_claude.py` | A stand-in for `claude` that prints the same stream-json. The apps use it in their chat tests. For a PDF, EDIT adds a comment with `pdfview add`. For a .tex file, EDIT suggests a change with `texview suggest`, and the Oracle replies with `texview reply`. For a plate (the prompt `/answer-plate ID`), the Oracle replies with `plateview reply`. For `/improve implement` and `/improve change`, it adds a line to `README.md` and commits it. |

## Rules

- The kit holds mechanics only. Trust, grants, document formats, and the way the page shows a document stay in the apps.
- A change in a `.py` file of the kit restarts the running servers of all the apps. Check the syntax first: a file that does not compile does not restart them.
- Run the chat tests of all the apps after each change: `tests/chat_browser_test.py` in `mdview` and in `pyview`, `tests/blocks_browser_test.py` in `mdview`, `tests/chat_test.py` in `pyview`, `tests/browser_test.py` in `pdfview`, `pageview` and `plateview`, `tests/improve_test.py pdfview|mdview|pyview|pageview` in `viewkit`, and `tests/network_test.py` in `pyview` after a change of `Net`.
- A computer that runs `pyview --remote` needs `viewkit` next to `pyview` there too.

## Tests

The tests of the apps cover the kit. The kit has one test of its own, `tests/improve_test.py`. It tests the automatic loop of the notes for one app, on copies of the app and of the kit. Run all of them after a change:

```
cd ~/tools/viewers/pyview && python3 tests/chat_test.py                                    # the chat on the server
cd ~/tools/viewers/pyview && uv run --with playwright python tests/chat_browser_test.py    # the chat panel, real browser
cd ~/tools/viewers/mdview && uv run --with playwright python tests/chat_browser_test.py    # the chat panel, real browser
cd ~/tools/viewers/mdview && uv run --with playwright python tests/blocks_browser_test.py  # the tables and blocks of mdview
cd ~/tools/viewers/pdfview && uv run --with playwright python tests/browser_test.py        # the viewer and its chat
cd ~/tools/viewers/pdfview && uv run --with playwright python tests/samples_test.py        # the sample PDFs
cd ~/tools/viewers/viewkit && for a in pdfview mdview pyview pageview; do uv run --with playwright python tests/improve_test.py $a; done   # the loop
cd ~/tools/viewers/viewkit && for a in pdfview mdview pyview pageview; do uv run --with playwright python tests/improve_test.py $a --mono; done   # the loop in viewers, local tracker
cd ~/tools/viewers/viewkit && python3 tests/notes_test.py                                  # the tracker of the notes
cd ~/tools/viewers/pageview && python3 tests/test_ops.py                                   # pageview without a server
cd ~/tools/viewers/pageview && uv run --with playwright python tests/browser_test.py       # the viewer and its chat
cd ~/tools/viewers/pyview && python3 tests/network_test.py                                 # pyview on the Tailscale address
cd ~/tools/viewers/plateview && python3 tests/test_ops.py                                  # plateview without a server
cd ~/tools/viewers/plateview && uv run --with playwright python tests/browser_test.py      # plates in a real browser
cd ~/tools/viewers/texview && python3 tests/test_ops.py                                   # texview without a server (needs latexmk)
cd ~/tools/viewers/texview && uv run --with playwright python tests/browser_test.py       # the editor, SyncTeX, changes, the chat
```

## Not shared yet

- **Chat markup and styles.** Each app keeps the HTML and the CSS of the chat panel, because the apps look different. The panel finds its elements by their ids (`chatOpen`, `chatBox`, `chatNew`, `chatMin`, `chatMsgs`, `chatCtx`, `chatAsk`, `chatText`, `chatSend`).
- **The answer renderer.** mdview gives `chatMd`, and pyview gives `mdRender`. pdfview uses `kit.md`.
- **MathJax.** mdview and pyview still use their own copies, not the copy in `web/vendor/`.
- **The comment sidebar.** The two `renderThreads` functions are too different. The plan is to share only the thread card.
